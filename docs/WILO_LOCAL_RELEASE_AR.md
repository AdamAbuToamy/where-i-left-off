# WILO المحلي — إصدار 2026-10-25

## ما تغيّر

المحلي هو العرض الافتراضي منذ أول فتح. يبدأ تنزيل النموذج بعد موافقة المستخدم، ويتولى الموقع التنزيل والتخزين المؤقت وتهيئة العامل. تتم استعادة اختيار المستخدم السابق تلقائيًا، دون إرسال الطلبات إلى السحابة عند فشل المحلي. يبقى السحابي اختيارًا صريحًا منفصلًا وله حدود مزوده.

الموقع والاختبار يستخدمان نفس `LocalAssistantModel` ونفس تعريف `shared/localRelease.mjs`: Qwen3-4B-q4f16_1-MLC، وWebLLM 0.2.86، وسياق 16384، وبذرة 7، ومخرجات حتى 4096، وtemperature=0.1، مع تعطيل thinking. هذا اختيار مرشح للاختبار، وليس ادعاء أنه نجح في الـ618.

الاختبار لا يستخدم Ollama أو Cloudflare أو Groq. لا ترسل توقعات الاختبارات إلى النموذج. تُرسل إليه تعليمات الحالة وبيانات الحساب الاصطناعية فقط، ثم يقارن Node الرد الحقيقي بالمخرجات المطلوبة. الإضافة والتعديل والحذف تبقى عبر مخطط العمليات والتحقق والمراجعة والحفظ المعتادين.

أُصلح الاحتفاظ بآخر معرّفات محفوظة بعد رد فاشل، وأضيف اختبار للإنشاء ثم «delete them» من الواجهة يثبت تجهيز البطاقة والقسم من إيصال الحفظ دون طلب استدلال آخر. لا تُخفى التغييرات الجزئية خلف رسالة نجاح.

## الاختبار والنشر من Ubuntu

```bash
cd ~/wilo-test &&
git fetch origin fix/wilo-local-release-20261025 &&
git switch fix/wilo-local-release-20261025 &&
git pull --ff-only origin fix/wilo-local-release-20261025 &&
npm ci &&
npx playwright install --with-deps chromium &&
node scripts/test-assistant-browser.mjs --limit=618 --resume --persist --deploy
```

يشغّل الأمر المتصفح آليًا داخل بيئة الاختبار؛ لا تحتاج إلى فتح localhost من Windows. يتطلب الاختبار معالج WebGPU متوافقًا وذاكرة كافية. يتطلب فحص الحفظ Java المثبت سابقًا لاختبارات Firebase. يتطلب النشر جلسة Firebase CLI الحالية وإعداد App Check الحالي؛ لا مفتاح نموذج AI.

التقرير: `assistant-acceptance-browser-report.json`. يحفظ رد كل حالة، والتتبع، والزمن، وسبب الفشل. `--resume` يعيد الحالات غير الناجحة ولا يعيد نجاحًا من مصدر أو نموذج مختلف. تغير المصدر يحفظ التقرير السابق ويبدأ تقييمًا جديدًا.

النشر ممنوع في السكربت حتى تنجح الحالات الـ618 بالنموذج الحقيقي، ثم يعاد تشغيل ردودها نفسها عبر AssistantRepository في محاكي Firestore، مع التحقق من إعادة القراءة. بعدها فقط يُبنى الموقع ويُنشر Hosting إلى الهدف الحالي `production`، ويُفحص `wilo-release.json` المنشور. لا تُغيّر قواعد Firestore أو بيانات الحسابات بهذه الخطوات، ويبقى ظهور WILO لحساب الإدارة الموثّق.
