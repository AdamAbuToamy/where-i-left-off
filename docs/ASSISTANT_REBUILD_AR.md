# إعادة بناء ربط المساعد — 24 أكتوبر 2026

المطلوب مساعد يفهم الرسالة ويختار دوال الموقع، ثم ينفّذ الموقع عمليات الإضافة والتعديل والحذف والجدول والإعدادات بعد المراجعة. النموذج لا يكتب في Firebase مباشرة، ولا تُعامل عبارته كإيصال حفظ.

## ما تقوله المصادر الرسمية

| المصدر | النتيجة المستخدمة في التصميم |
|---|---|
| [Groq — Local Tool Calling](https://console.groq.com/docs/tool-use/local-tool-calling) | يحدد النموذج اسم الدالة ومعاملاتها؛ التطبيق هو المسؤول عن التنفيذ ونتيجته. |
| [Groq — Supported Tool Use](https://console.groq.com/docs/tool-use/overview) | GPT-OSS-120B يدعم الدوال. عدم دعمه الدوال المتوازية لا يمنع إرسال دفعة عمليات داخل دالة واحدة. |
| [Google — Function Calling](https://ai.google.dev/gemini-api/docs/function-calling) | يجب فصل فهم الطلب عن التنفيذ: تعريف دوال، اختيار ومعاملات، تنفيذ كود التطبيق، ثم عرض النتيجة. تغيير مزود النموذج وحده لا يصلح ربط التنفيذ. |
| [Firebase — Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens) | الخادم يتحقق من هوية المستخدم والتوقيع والمشروع؛ لا يثق بمعرّف حساب يرسله النموذج. |
| [Firebase — Custom Backend App Check](https://firebase.google.com/docs/app-check/custom-resource-backend) | تحقق التطبيق مستقل عن هوية المستخدم؛ يلزم الاحتفاظ بالتحققين وعدم تعطيل أي منهما لإخفاء المشكلة. |
| [Firebase — Web Custom Resources](https://firebase.google.com/docs/app-check/web/custom-resource) | يُرسل رمز App Check إلى الخادم في ترويسة منفصلة ويُتحقق منه هناك. |
| [Cloudflare — Errors](https://developers.cloudflare.com/workers-ai/platform/errors/) | رموز HTTP المختلفة، ومنها 429، قد تعني حدودًا أو سعة مؤقتة؛ لا يصح وصف كل فشل بأنه نفاد الحصة. |

## عيوب مؤكدة في الربط السابق

1. اختبارات النموذج الاصطناعية تجاوزت هوية المستخدم وApp Check وفحص حساب خدمة Firebase وتهيئة Worker؛ نجاحها لم يثبت اتصال الموقع المنشور.
2. Worker كان يحوّل فشل حساب الخدمة/فحص Auth/قاعدة البيانات إلى `request-failed`، والواجهة كانت تحوّل الأخطاء غير `ai-*` إلى رسالة دفع عامة. ضاع السبب على الحدّين.
3. قراءة حساب الموقع، App Check، إعداد عنوان الخادم، الشبكة والخادم كانت تشترك في رسالة واجهة واحدة؛ الصورة المرفقة وحدها لا تحدد أيها فشل.
4. بعض رسائل الشات كانت تمر في محلل أوامر قبل النموذج؛ نجاحها لا يثبت عمل AI. أُزيل هذا التفريع من إرسال الشات. الاستيراد المنظم في صفحة الجامعة ودواله لا يتأثران.
5. لم يكن النشر يتحقق من توافق الواجهة مع إصدار Worker وCORS، ولا يعيد تجهيز جداول المساعد في إعداد Groq.

هذه عيوب مثبتة من الكود. لم يثبت بعد أي واحد منها سبّب طلب صاحب الحساب المصوّر تحديدًا؛ يجب التحقق من الجلسة المنشورة والطلب نفسه.

## المسار الجديد

- كل رسالة شات تذهب كاملة إلى مسار المساعد؛ لا استخراج عنوان بطاقة بجملة regex، ولا إسقاط بقية الرسالة في اختصار محلي.
- `AssistantApi` حد اتصال مستقل عن دعم Push: عنوان خاص، هوية، App Check، POST، تحليل الرد. يجدد الرمزين مرة واحدة عند 401، ولا يعيد رفض الحصة أو الصلاحيات كإصلاح لغوي.
- Worker يتحقق من JWT وApp Check، وتوفر الحساب، وجداول D1 وإعداد المزود، ثم يستدعي النموذج.
- Groq يستخدم استدعاء أدوات واحدًا لاقتراح دفعة عمليات الموقع الموجودة. لا يملك رمز Firebase ولا يغيّر قواعده. الكود يفحص المخطط والقيم والفهارس، ثم مخطط العميل يفحص المراجع والصلاحيات والتعارض.
- المراجعة ثم `AssistantRepository` تطبق دوال الموقع بمعاملة Firebase، وتعيد القراءة من الخادم للتحقق من إيصال كل تعديل. النتيجة المعروضة من الكود، لا ادعاء النموذج.
- كل خطأ يحمل مرحلة ثابتة ورمزًا وحالة HTTP ومعرّف طلب عشوائيًا؛ لا رموز دخول أو مفاتيح أو نصوص حساب. التقرير الذي ينسخه المستخدم يحتوي هذه البيانات الآمنة فقط.

## فحص الاتصال والنشر

عند الخطأ توجد تفاصيل اتصال وزر فحص. يقرأ بيانات الحساب فعليًا، ثم يرسل طلب صحة محميًا إلى نفس المسار. يفحص الخادم الهوية وApp Check وحساب الخدمة والقاعدة وإعداد المزود، ويعيد `inferenceTested:false`: الفحص لا يستهلك استدعاء نموذج ولا يدّعي أنه اختبر جودة AI أو الحفظ.

`setup-groq-assistant.mjs` يجهز جداول المساعد بأوامر CREATE IF NOT EXISTS، ويرفع المفتاح مباشرة عبر stdin إلى Worker Secret، ويحافظ على D1 والطوابير، وينشر Worker ثم يتحقق من الإصدار وCORS ويجهز `assistant-config.json`. سكربت نشر الواجهة يرفض الاستمرار إذا كان Worker غير متوافق. الإعداد العام ليس سريًا، ويُرسل no-store ويُستثنى من كاش Service Worker.

## حدود الأدلة

اختبار HTTP الجديد يستخدم توقيعات JWT وApp Check حقيقية بمفاتيح اختبار مؤقتة وSQLite فعلية لمسار Worker؛ استجابة Groq وفحص حساب خدمة الإنتاج محقونان. اختبار الحفظ المتكامل يمر من عميل API إلى Worker والتحقق من التوقيعات ثم محلل الدوال ومعاملة Firebase Emulator وقراءة جديدة، مع استجابة نموذج محقونة. هذه الاختبارات تفحص الربط والتنفيذ؛ ليست اختبارًا حيًا لمزود Groq أو IAM في حساب المالك.

الطلب الحي السابق أعاد القيم الثلاث المطلوبة خلال نحو 1.5 ثانية، لكنه لم يكن طلبًا من صفحة المالك إلى Worker المنشور. لا يجوز تسميته إثباتًا لعمل الموقع كاملًا. التحقق الإنتاجي النهائي يحتاج جلسة مالك متاحة ونشر Worker والواجهة المتوافقين، ثم تنفيذ طلب حقيقي والتحقق بعد تحديث الصفحة. لا يوجد وعد بخدمة سحابية مجانية غير محدودة.

## سبب HTTP 503 مع status:0 الذي ثبت بعد النشر

أُعيد إنتاج الخطأ في workerd بتاريخ 24 أكتوبر: استدعاء fetch مع `redirect:'error'` يرمي TypeError: Invalid redirect value قبل إرسال أي طلب خارجي. Node يدعم هذه القيمة، ولذلك نجحت اختبارات Node السابقة. هذا يفسر فشل Groq في بيئة Worker، ولا يثبت نفاد الحصة. التعديل يستخدم `redirect:'manual'` ويرفض ردود 3xx دون اتباع Location؛ لا يُرسل المفتاح إلى وجهة التحويل.

اختبار `push-worker/assistant-runtime.test.mjs` ينفذ المهايئ الحقيقي داخل workerd، ويمرر مخطط الدوال الكامل، مع HTTP خارجي محقون. يتحقق من الوصول إلى Groq وGoogle ورفض تحويل 302 دون إرسال المفتاح إلى الوجهة الثانية. هذا اختبار runtime حقيقي، لكنه ليس استنتاجًا حيًا من نموذج ولا اختبار حفظ إنتاجي.

لمستخدم Groq الحالي يكفي نشر Worker المصحح؛ لا يلزم مفتاح جديد أو تغيير إلى Gemini لإصلاح هذا الخطأ المحدد. يظل Gemini خيارًا صريحًا كما في دليل إعداده.
